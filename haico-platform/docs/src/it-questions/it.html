DEMO Enterprise Platform — IT questions, and how I answer them

Short, plain answers for the questions IT and the managers are likely to ask about the demo. The demo is a working model of the design; the live system is built on the same rules.

Demo: Netlify site · fictional data
One company or a group of companies
What it is
What am I looking at — is this the real system?

A working demo. Every screen, approval step and rule behaves the way the live system will, but it runs in the browser with fictional people and figures so we can test the process first.

Why does it ask "one company or a group" first?

So it can be shown the way an organization is set up. One company keeps one set of books with eight departments; a group keeps separate books per company with inter-company charges. The people, departments and approvals are the same in both.

Where does the data live right now?

Only in the browser of the person using the demo. Nothing is sent anywhere. Clearing the browser's site data resets it to the starting data. The live system keeps everything in a database on our side.

How it's built
Front endWhat people see in the browser. Plain HTML, CSS and JavaScript — the same screens as the demo, so nothing has to be redesigned. Works in Edge and Chrome, on a laptop or a phone.
Back endThe server that checks every action and applies the rules. TypeScript on Node.js — the same language as the front end, so one team maintains both. The screens talk to it through a small set of secured web requests (an API).
DatabasePostgreSQL, a standard free database used by banks and governments. One table per thing — employees, requests, approvals, journal lines — every change kept, never overwritten.
Sign-inMicrosoft 365 (Entra ID). No separate passwords; a closed account is a closed door.
Email & filesSent through Microsoft 365. Attachments and PDFs stored in our own storage, not in the database.
HostingRuns in a container, so it can sit in our Azure tenant or with a Canadian provider — IT's choice, no redesign either way.
Why these and not something fancier?

They're the most common tools in the industry: any web developer can pick the work up, there are no licence fees, and they'll still be supported in ten years.

How does the demo become the real thing?

The demo already has the three layers: the screens, the rules, and a record of every action. Building the live system means moving the rules to the server and the records into the database — the screens stay. That's why the demo is worth testing hard now: every rule we agree here carries straight over.

Security and access
How do people sign in?

With their work account. The demo has no password — you pick a name — because the people are made up; the live system signs in through Microsoft 365, so there is no separate password to manage and leavers lose access when their account is closed.

Who can see what?

Each person has a role — employee, manager, HR, Finance, executive, administrator. The role decides their menus, and the server checks the same rules on every action, so a hidden button is never the only protection.

Are credit card numbers stored?

No. A credit card purchase records what was bought, who approved it and what Finance was charged. Card numbers, expiry dates and security codes are never entered, never stored and never emailed.

Is there an audit trail?

Yes. Every action — a request, an approval, a decline, a rate change, a stat holiday added — is written to the audit log with who did it and when. Financial and approval records are never deleted; they can only be cancelled or closed.

How it works
How does a request know who approves it?

From the organization chart. It goes to the person's supervisor. If that supervisor is on approved time off that day, it also goes to the next person up, and the first decision counts. Amounts over the limit add director level. Nobody approves their own request.

What happens if someone changes the rules — rates, limits?

Finance keeps the rates on one page. The Finance Manager changes them directly; anyone below sends a change for approval first. Every change is logged with the old and new values. Requests already sent keep the rates they were made with.

How does it connect to payroll and the ledger?

Approved timesheets feed the pay run; banked overtime is credited to time off instead of paid. Processed purchases and paid claims post to the general ledger with their account and department, so reports line up without re-keying.

Running it
Where will it be hosted? Who supports it?

The demo is on Netlify. The live system can run in our Azure tenant or with a Canadian provider — IT's decision; the design doesn't depend on it. Support is like any internal web app: access through IT, process questions through Finance and HR.

Emails and calendar — are they real?

In the demo, Email (Inbox, Sent, Drafts and the other folders) and Calendar show the platform's own messages and dates plus sample entries, and nothing is sent. In the live system they connect to each person's Microsoft 365 mailbox and Outlook calendar. The wording of system emails is editable by an administrator.

Backups, phones, changes?

Backups follow IT's normal schedule for the chosen host, and the full change history means any record can be traced back. The screens adjust to a phone. Changes are collected on each page and built in reviewed rounds — how this demo itself was refined.

If I don't know: "That's an IT setup decision — I'll bring it to you with the options rather than guess." Hosting, backup schedule, and single sign-on setup are the three to hand to IT.

Three things to repeat: no card numbers stored · the server checks every permission · nothing financial is ever deleted.
